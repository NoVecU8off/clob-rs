проект следует [семантическому версионированию](https://semver.org/lang/ru/).

## [Unreleased]

### Добавлено

- **Счёт/владелец заявки и self-trade prevention (STP) (v0.5, фаза 1).** Заявка получила
  опциональные поля `owner: AccountId` (новый примитив-`u64` в `src/types.rs`; `0` — аноним /
  не задан) и `stp: StpMode` (`Off` | `CancelTaker` | `CancelMaker` | `CancelBoth`), задаваемые
  билдерами `NewOrder::with_owner(id)` / `with_stp(mode)`; конструкторы по умолчанию ставят
  `owner = 0`, `stp = Off`, поэтому существующее поведение не меняется (STP — строго opt-in).
  **Self-trade prevention** срабатывает в момент сведения, по каждому встречному мейкеру: при
  `taker.stp != Off && taker.owner != 0 && taker.owner == maker.owner` вместо сделки применяется
  политика **агрессора** (taker governs) — `stp` стоящего мейкера не читается, ему достаточно
  совпасть по владельцу. `CancelTaker` снимает остаток агрессора (`Canceled`), мейкер цел;
  `CancelMaker` снимает встреченный стоящий ордер (`Canceled`) и агрессор идёт дальше по очереди;
  `CancelBoth` снимает оба. Решение принимается **по каждому** мейкеру при проходе уровня, поэтому
  чужая ликвидность сводится нормально, а самопересечение разруливается точечно. STP применяется и
  к **сработавшему стопу** (он несёт свои `owner` / `stp` и на активации действует как агрессор).
  `owner` хранится инлайном на `RestingOrder` (кеш-локально для цикла сведения) и **переживает**
  снимок и реплей: журнал и снимок версионированы (`CLBW` / `CLBS` → версия `2`); запись `New`
  несёт `owner` варинтом и `stp` в свободных битах байта флагов. Проекция market data остаётся
  **обезличенной** — `owner` в L2 / L3 / ленту сделок не попадает. Новые публичные типы —
  `AccountId`, `StpMode`, `MatchOutcome`. Детерминированное ядро не нарушено (новый `u64`
  сравнивается только на равенство, итерация `HashMap` на вывод не влияет), новых зависимостей нет
  (только `std`). Известные границы: STP проверяется на `New` (не на `Modify` — amend пере-сводится
  без STP); предпроверка `Fok` / post-only считает встречный объём целиком, не вычитая собственную
  ликвидность. Закрывает первый пункт v0.5; pre-trade risk и комиссии — следующие.
- **Market data: инкрементальные L3-обновления и сквозная нумерация каналов (v0.4, фаза 4 — закрывает v0.4).**
  Новый модуль `src/l3feed.rs` и публичные типы `L3Delta` (`Added { id, side, price, qty }` /
  `Reduced { id, qty }` / `Removed { id }`), `L3Update { seq, deltas }` и `L3Feed` — инкрементальный
  **market-by-order**-канал с позицией в очереди. `L3Feed::apply(&events, book)` превращает события
  одной команды в пер-заявочные дельты: затронутые ценовые уровни выводятся из событий (как у `L2Feed`),
  а порядок очереди внутри каждого уровня сверяется с книгой через новый read-аксессор
  `OrderBook::level_orders(side, price)`. Survivors (заявки, сохранившие позицию) дают `Reduced`,
  выбывшие — `Removed`, новые/переставленные в хвост — `Added`; дельты эмитятся в порядке
  remove → reduce → add, поэтому **долив айсберга** и **потеря приоритета при amend** (перестановка в
  хвост уровня) корректно выражаются как remove-then-add и точно воспроизводят FIFO книги у потребителя.
  `L3Feed::new()` стартует с пустой книги, `L3Feed::from_book(book)` — посев из снимка с тем же `seq`.
  Проекция остаётся **публичной и обезличенной**: отдаётся только видимый peak айсберга, скрытый резерв в
  дельты не попадает.
  **Сквозная нумерация data-каналов.** Все каналы market data якорятся на `seq` команды через единый
  `command_seq` (один источник истины вместо разрозненного вывода): снимки `l2_snapshot` / `l3_snapshot`
  несут `Clob::current_seq()`, инкременты `L2Update` / `L3Update` и принты `TapeTrade` — тот же `seq`
  команды. Для одной команды все каналы несут **один** `seq`, так что потребитель применяет инкременты с
  `seq` больше снимочного и сводит каналы между собой по общему якорю. Новые публичные типы — `L3Delta`,
  `L3Feed`, `L3Update`; добавлен read-аксессор `OrderBook::level_orders`. Детерминированное ядро не
  изменено, новых зависимостей нет (только `std`). С этим шагом **v0.4 (Market data) закрыт**.
- **Market data: лента сделок (trade tape) (v0.4, фаза 3).** Новый модуль `src/tape.rs` и публичные
  типы `TapeTrade` (обезличенный принт: `seq` + `price` + `qty` + `taker_side`) и `TradeTape` —
  отдельный data-канал поверх потока событий. `TradeTape::apply(&events)` извлекает по одному принту
  на каждый `Event::Trade` (в порядке исполнения — при свипе нескольких уровней best price first),
  возвращает принты команды и копит их в ограниченной кольцевой истории: `new()` — без предела,
  `bounded(cap)` — только последние `cap`; чтение — `recent()` (от старых к новым), `last()`, `len()`,
  `is_empty()`. В отличие от L2/L3-проекций канал **book-free**: `apply` берёт только `&[Event]` и к
  книге не обращается — ленту может вести потребитель, видящий лишь поток событий. Каждый принт несёт
  `seq` команды — общий якорь с книжным каналом (`L2Update` и снимки). Обезличенность — о владельце и
  идентификаторах (id заявок в ленту не попадают); исполненный объём публичен и печатается полностью,
  поэтому проход по айсбергу даёт принт на каждый сведённый слой, включая объём из скрытого резерва
  (книга прячет *стоящий* резерв, лента печатает *исполненное*). Детерминированное ядро не изменено,
  новых зависимостей нет (только `std`). Новые публичные типы — `TapeTrade`, `TradeTape`. Оставшиеся
  шаги v0.4 (L3-инкремент и сквозная нумерация каналов) закрыты следующей фазой.
- **Market data: инкрементальные L2-обновления (v0.4, фаза 2).** Новые публичные типы
  `L2Update` (разреженный кадр: `seq` + `bids` / `asks` из `L2Level`, уровень с `qty == 0`
  означает удаление, цены best-first на каждой стороне) и `L2Feed` — stateful read-проекция,
  превращающая `Vec<Event>` одной команды в дельты **только изменённых** ценовых уровней.
  `L2Feed::apply(&events, book)` выводит затронутые уровни из событий (сторона мейкера у `Trade`;
  внутреннее зеркало `order_id → (side, price)` для `Resting` / `Modified` / `Canceled` / `Filled`,
  которые цену не несут) и сверяет новый агрегат каждого уровня с книгой — поэтому дельты точны
  даже там, где поток событий «молчит»: при **айсберг-доливе** (события нет, но долив всегда на
  трейд-цене, а та уже среди затронутых) и при **modify-репрайсе** (старый уровень добавляется по
  `Modified` до того, как `Resting` обновит зеркало на новую цену). `L2Feed::new()` стартует с
  пустой книги, `L2Feed::from_book(book)` — посев из текущего состояния (под пару к `l2_snapshot`
  с тем же `seq`): снимок задаёт базу, дельты держат её в синхроне без повторной пересылки всей
  книги. Кадр несёт `seq` команды — общий якорь со снимком. Проекция остаётся **публичной и
  обезличенной**: скрытый резерв айсберга в дельты не попадает. Добавлен один read-аксессор
  `OrderBook::level_qty(side, price)`; детерминированное ядро не изменено, новых зависимостей нет
  (только `std`). Новые публичные типы — `L2Update`, `L2Feed`. L3-инкремент, лента сделок и
  консистентность номеров последовательности между каналами — оставшиеся шаги v0.4.
- **Market data: снимки книги L2 и L3 (v0.4, фаза 1).** Два новых метода на `Clob`:
  `l2_snapshot(depth)` — **market-by-price**, агрегированная глубина по ценовым уровням
  (`L2Snapshot` с `bids` / `asks` из `L2Level { price, qty }`, лучшая цена первой, не более
  `depth` уровней на сторону), и `l3_snapshot()` — **market-by-order**, книга по отдельным
  заявкам (`L3Snapshot` из `L3Order { id, side, price, qty }`, best-first по цене и FIFO внутри
  уровня — видна позиция в очереди). Оба снимка тегируются текущим `seq` (`current_seq`), чтобы
  потребитель мог упорядочить их относительно будущих инкрементальных обновлений. Проекция
  **публичная и обезличенная**: для iceberg-заявок отдаётся только видимый peak — скрытый резерв
  в L2/L3 **не попадает**. L2 — агрегация L3 по цене (инвариант проверяется тестом). Реализовано
  как read-проекция в новом модуле `src/marketdata.rs` поверх публичных `book()` / `current_seq()`:
  детерминированное ядро не изменено, новых зависимостей нет (только `std`). Новые публичные типы —
  `L2Level`, `L2Snapshot`, `L3Order`, `L3Snapshot`. Инкрементальные обновления, лента сделок и
  консистентность номеров последовательности между каналами — следующие шаги v0.4.
- **Персистентность: снимки книги (v0.3, фаза 2).** Новый метод
  `PersistentClob::checkpoint()` пишет на диск **снимок** полного детерминированного
  состояния (`seq` и `next_order_id` секвенсора, цена последней сделки, все стоящие заявки
  в порядке приоритета вместе со скрытыми резервами айсбергов, спящие стоп-заявки) и затем
  усекает журнал до хвоста (ротация сегмента с новым `base_seq`). Восстановление
  (`PersistentClob::open`) теперь грузит снимок и **переигрывает только хвост** журнала, а
  не весь поток с нуля. Формат снимка — собственный бинарный, `std`-only: заголовок
  `magic "CLBS"` + версия, varint-поля, общий кадр с CRC32 (тот же кодек, что у журнала).
  Запись снимка атомарна (запись во временный файл → `fsync` → `rename`). Согласование
  снимка и журнала идемпотентно по `seq`: при восстановлении применяются только команды
  журнала с `seq` больше, чем покрывает снимок, поэтому прерванный посреди чекпойнт (снимок
  записан, журнал ещё не повёрнут) не приводит ни к двойному применению, ни к потере команд.
  Битый снимок (CRC не сходится) отклоняется как `JournalError::CorruptSnapshot` — журнал
  при этом остаётся источником истины. Снимок хранится рядом с журналом (`<journal>.snap`),
  публичный API дополнен одним методом `checkpoint`; новых зависимостей нет (только `std`),
  детерминированное ядро не изменено. Новый вариант ошибки — `JournalError::CorruptSnapshot`.
- **Персистентность: журнал команд и реплей (v0.3, фаза 1).** Новая обёртка
  `PersistentClob` оборачивает `Clob` и ведёт write-ahead журнал входных команд: каждая
  команда сериализуется и сбрасывается на диск (`fsync`) **до** возврата событий, поэтому
  подтверждённая заявка переживает падение процесса. При открытии (`PersistentClob::open`)
  состояние восстанавливается **реплеем** — записанный поток команд переподаётся в свежий
  `Clob`; благодаря детерминизму книга, `order_id` и `seq` воспроизводятся точно (отклонённые
  gateway команды тоже журналируются — они расходуют `seq`). Формат журнала — собственный
  бинарный, `std`-only: заголовок сегмента `magic "CLBW"` + версия формата, записи команд с
  varint-полями, блоки кадрируются длиной + CRC32 (групповой коммит — `submit_batch`).
  Прерванная на полузаписи последняя запись отсекается по CRC при восстановлении.
  Низкоуровневый доступ: `Journal` (писатель), `read_commands` (читатель). Новые публичные
  типы — `PersistentClob`, `Journal`, `JournalError`, `CodecError`, функция `read_commands`.
  Детерминированное ядро не изменено: персистентность — слой над `Clob`, без часов и потоков;
  новых зависимостей нет (только `std`). Снимки книги для ускорения восстановления — следующий
  шаг (фаза 2).
- **Iceberg (`OrderType::Iceberg { display }`)** — заявка с видимой частью (peak,
  `display`) и скрытым резервом. Конструктор `NewOrder::iceberg(side, price, qty, display)`,
  где `qty` — полный объём, `display` — размер видимой части. В книге, `depth()`,
  `len()`, `total_qty` и `available_qty()` учитывается **только видимый peak**; резерв
  хранится в стороннем индексе книги и не показывается. Когда видимый peak полностью
  сводится, из резерва доливается новый peak `min(display, hidden)` и ставится **в хвост**
  своего ценового уровня — теряя временной приоритет перед уже отображёнными заявками
  (стандартное правило айсберга). Достаточно крупный тейкер «прометает» весь айсберг
  (включая скрытую часть) за один проход, послойно. Долив **не порождает событий**
  (отражается в `depth()`); инкрементальные обновления — отдельный пункт v0.4. Как тейкер
  айсберг сводится на полный `qty`, как обычный лимит. Gateway отклоняет `display == 0`
  (`ZeroQuantity`) и `price == 0` (`InvalidPrice`); `display >= qty` сводится к обычной
  полностью видимой заявке. Для `Fok` скрытый резерв **не учитывается** в проверке
  ликвидности (считается только отображённый объём). `Modify` айсберга трактует `qty`
  как новый полный объём, сохраняет `display` и всегда переставляет заявку заново (теряя
  приоритет). Новых `Event` / `RejectReason` не добавлено.
- **Stop и stop-limit (`OrderType::Stop` / `OrderType::StopLimit`)** — отложенные заявки с триггерной ценой. Конструкторы `NewOrder::stop(side, trigger, qty)` (на срабатывании ведёт себя как рыночная) и `NewOrder::stop_limit(side, trigger, limit, qty)` (на срабатывании — лимитная по цене `limit`). Gateway отклоняет стоп с `trigger == 0` и стоп-лимит с `trigger == 0` или `price == 0` как `InvalidPrice`. Срабатывание привязано к **цене последней сделки**: buy-stop активируется при `last >= trigger`, sell-stop — при `last <= trigger`. До срабатывания заявка «спит» в отдельной книге стопов и **не видна** в `depth()` / `len()` книги; если рынок уже за триггером, стоп срабатывает сразу при приёме. Активация **каскадная**: сделки сработавшей заявки двигают цену и могут активировать следующие стопы (порядок активации — по времени приёма, детерминированно). `Cancel` снимает спящий стоп; `Modify` спящего стопа пока не поддерживается (отклоняется как `UnknownOrder`).
- **Событие `Triggered`** — стоп-заявка сработала и сейчас проходит сведение; далее идут обычные события исхода (`Trade` / `Resting` / `Filled` / `Canceled`), как у `New` после `Accepted`. События активации тегируются `seq` текущей команды, идентичность заявки — по `order_id`.
- **`Clob::pending_stops()`** — число спящих (ещё не сработавших) стоп-заявок.
- **Post-only (`TimeInForce::PostOnly`)** — заявка «только мейкер»: если лимит немедленно пересёк бы спред, она отклоняется (`RejectReason::WouldCross`) до `Accepted` и в книгу не попадает; иначе ведёт себя как `Gtc` и встаёт в книгу. Проверка — в движке, до приёма (как предпроверка `Fok`); для `Market` пересечение считается всегда.
- **Команда `Modify` (amend)** — изменение цены и/или количества стоящей заявки (`Command::Modify`, `ModifyOrder::new`). Уменьшение количества при той же цене сохраняет временной приоритет (правка на месте за `O(1)`); смена цены или увеличение количества теряет приоритет — заявка снимается и заново проходит сведение с тем же `order_id`, при пересечении спреда исполняется.
- **Событие `Modified`** — подтверждение приёма `Modify`; далее следуют события исхода (`Resting` / `Trade` / `Filled`), как у `New` после `Accepted`.

### Изменено

- **Order book** — слаб-арена с интрузивным FIFO-списком (`Node`, `Slab`, `PriceLevel` и операции `link_back` / `unlink`) вынесена из `src/book.rs` в новый модуль `src/slab.rs` (разбиение по ответственности: `book.rs` остаётся под лимитом в 400 строк). Поведение и сложность не изменились.
- **Order book** — внутри ценового уровня интрузивный двусвязный FIFO-список вместо `VecDeque`; узлы заявок хранятся в общей арене (слаб) со списком свободных слотов. Отмена внутри уровня теперь `O(1)` вместо `O(n)`.
- **Matching Engine** — убрана аллокация `Vec` под идентификаторы исполненных заявок: мейкер снимается из индекса прямо в цикле сведения, а слот узла возвращается в пул.
- **Matching Engine** — общий путь сведения (предпроверки TIF, матчинг, постановка остатка/отмена) вынесен в `settle` / `precheck` и переиспользуется новыми заявками, amend и активацией стопов; добавлены книга стопов и каскадная активация по цене последней сделки. `Modify`, породивший сделку, теперь тоже может активировать стопы.

Остальное запланированное см. в [ROADMAP.md](ROADMAP.md).

## [0.1.0] — 2026-06-20

Первый релиз. Детерминированное ядро CLOB с конвейером
`Gateway → Sequencer → Matching Engine → Output`.

### Добавлено

- **Конвейер `Clob`** — единая точка входа `submit()` / `submit_into()`, связывающая все стадии.
- **Gateway** — валидация заявок: отказ при нулевом количестве (`ZeroQuantity`) и нулевой цене лимитной заявки (`InvalidPrice`).
- **Sequencer** — монотонные номера последовательности и идентификаторы заявок для детерминированного порядка.
- **Matching Engine** — сведение по price-time priority (FIFO внутри ценового уровня).
- **Order book** — `BTreeMap` ценовых уровней по каждой стороне, `VecDeque` для FIFO внутри уровня, `HashMap` индекс заявок для отмены.
- **Типы заявок** — `Limit`, `Market`.
- **Time-in-force** — `Gtc`, `Ioc`, `Fok`.
- **События** — `Accepted`, `Trade`, `Resting`, `Filled`, `Canceled`, `Rejected`.
- **Доступ к книге** — `best_bid`, `best_ask`, `spread`, `depth`, `len`, `contains`, `available_qty`.
- **Примеры** — `examples/basic.rs` (демонстрация событий и книги), `examples/throughput.rs` (нагрузочный прогон).
- **Тесты** — 12 интеграционных тестов на матчинг, приоритет, TIF, отмену и инварианты книги.
- **Документация** — папка `docs/` (статус, архитектура, журнал обновлений, roadmap).

### Особенности реализации

- Целочисленные цены и количества (`u64`), без чисел с плавающей точкой.
- Ядро без внешних зависимостей (только `std`).
- Редакция Rust 2024; `release`-профиль с LTO и `panic = "abort"`.
