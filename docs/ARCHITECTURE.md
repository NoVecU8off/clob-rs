# Архитектура

## Обзор

`clob` — детерминированный движок центральной книги лимитных заявок, оформленный как
конвейер из четырёх стадий. Каждая команда проходит стадии по порядку и порождает
вектор событий.

```
                    ┌──────────┐   ┌────────────┐   ┌──────────────────┐   ┌──────────┐
   Command  ─────▶  │ Gateway  │─▶ │ Sequencer  │─▶ │ Matching Engine  │─▶ │  Output  │ ─────▶ Vec<Event>
(New/Cancel/Modify) └──────────┘   └────────────┘   └──────────────────┘   └──────────┘
                    валидация и     присвоение        ордербук +            события:
                    нормализация    seq и order_id    price-time матчинг    Trade / Resting / ...
```

Связывает стадии тип [`Clob`](../src/clob.rs). Публичный API минимален:

```rust
let mut clob = Clob::new();
let events: Vec<Event> = clob.submit(Command::New(NewOrder::limit(Side::Buy, 101, 5)));
```

## Принципы

1. **Детерминизм.** Один инструмент обрабатывается одним потоком в строгом порядке
   номеров последовательности. Одинаковый вход → одинаковый выход, всегда. Это даёт
   воспроизводимость, аудит, реплики и (в перспективе) восстановление по журналу.
2. **Целочисленная математика.** Цены — в тиках, количества — в лотах (`u64`).
   Никаких `f64`: денежные расчёты должны быть точными и повторяемыми.
3. **События на выходе, а не мутации на входе.** Движок не отдаёт наружу изменяемое
   состояние — он возвращает поток событий, естественный для клиринга, market data и журнала.
4. **Параллелизм — через шардирование по инструментам**, а не через потоки внутри одной книги.

## Стадии конвейера

### Gateway — [src/gateway.rs](../src/gateway.rs)

Первый барьер. Проверяет корректность команды до того, как она дойдёт до движка:

- `qty == 0` → `RejectReason::ZeroQuantity`;
- нулевая цена → `RejectReason::InvalidPrice`: лимитная заявка с `price == 0`, стоп с
  `trigger == 0`, стоп-лимит с `trigger == 0` или `price == 0`;
- `Modify` с `qty == 0` или `price == 0` отклоняется по тем же правилам;
- отмена проходит всегда (существование заявки проверяет движок).

Сюда же логично добавлять правила инструмента (размер тика/лота, ценовые коридоры,
pre-trade risk) — структура без полей оставлена расширяемой.

### Sequencer — [src/sequencer.rs](../src/sequencer.rs)

Присваивает каждому событию монотонный `seq`, а каждой новой заявке — уникальный
`order_id` (начиная с 1). Это сердце детерминизма: порядок фиксируется здесь и далее
не меняется. `seq` используется и как логическая метка времени.

### Matching Engine — [src/engine.rs](../src/engine.rs)

Применяет провалидированную и пронумерованную команду к ордербуку и порождает события.
Отвечает за семантику типов заявок и time-in-force:

- **FOK** — предпроверка `available_qty`; если полностью исполнить нельзя, заявка
  отклоняется (`InsufficientLiquidity`) и в книгу не попадает.
- **Post-only** — предпроверка `would_cross`; если лимит немедленно пересёк бы спред,
  заявка отклоняется (`WouldCross`) до `Accepted` и в книгу не попадает (`Market`
  считается пересечением всегда). Иначе ведёт себя как `Gtc` — встаёт в книгу.
- Иначе — `Accepted`, затем сведение со встречной стороной (события `Trade`).
- После сведения:
  - остаток `0` → `Filled`;
  - остаток `>0` и это `Limit` + (`Gtc` / `PostOnly`) → встаёт в книгу (`Resting`);
  - иначе (`Market`, `Ioc`, недопрошедший `Fok`) → остаток отменяется (`Canceled`).

Отмена: `execute_cancel` снимает заявку из книги (`Canceled`) либо отклоняет
несуществующую (`UnknownOrder`).

Изменение (amend): `execute_modify` находит стоящую заявку (иначе `UnknownOrder`) и
эмитит `Modified`. Уменьшение количества при той же цене — правка на месте за `O(1)`
с сохранением приоритета (далее `Resting` с новым объёмом). Смена цены или увеличение
количества — потеря приоритета: заявка снимается и с тем же `order_id` заново проходит
сведение (при пересечении спреда — `Trade`, затем `Filled` или `Resting`). Так книга
после amend остаётся нескрещённой.

Стоп-заявки (`Stop` / `StopLimit`) не попадают в основную книгу сразу: движок «паркует»
их в отдельной книге стопов ([src/stops.rs](../src/stops.rs)) и эмитит `Accepted`. Триггер
привязан к **цене последней сделки**: buy-stop активируется при `last >= trigger`, sell-stop —
при `last <= trigger`. После любой команды, породившей сделку (а также сразу после приёма
стопа), движок прогоняет сработавшие стопы: по каждому — `Triggered`, затем обычное сведение
(`Stop` — как рыночная, `StopLimit` — как лимит с тем же TIF) через тот же путь `settle`/`precheck`,
что и `New`. Сделки активированной заявки двигают цену последней сделки, поэтому активация
**каскадна**: один стоп может потянуть следующий. Каскад детерминирован (порядок активации —
по времени приёма) и конечен (множество спящих стопов строго убывает). События активации
тегируются `seq` текущей команды, заявка опознаётся по `order_id`. `Cancel` снимает спящий
стоп; `Modify` спящего стопа пока отклоняется (`UnknownOrder`).

### Output — [src/output.rs](../src/output.rs)

Единый перечень событий `Event`:

| Событие | Когда |
| --- | --- |
| `Accepted` | заявка принята движком |
| `Trade` | состоялась сделка (тейкер ↔ мейкер, цена, объём) |
| `Resting` | остаток встал в книгу |
| `Filled` | заявка исполнена полностью |
| `Canceled` | заявка/остаток снят |
| `Modified` | заявка изменена (amend); далее идут события исхода |
| `Triggered` | стоп-заявка сработала; далее идут события исхода |
| `Rejected` | отказ (gateway, нехватка ликвидности для FOK или пересечение спреда для post-only) |

## Структура ордербука — [src/book.rs](../src/book.rs)

```
                 OrderBook
   ┌─────────────────────────────────────┐
   │ bids:  BTreeMap<Price, PriceLevel>   │   максимальная цена = лучший bid
   │ asks:  BTreeMap<Price, PriceLevel>   │   минимальная цена = лучший ask
   │ slab:  Vec<Node> + список свободных   │   арена узлов заявок
   │ index: HashMap<OrderId, {side, slot}> │   поиск узла для отмены за O(1)
   └─────────────────────────────────────┘
                    │
                    ▼  PriceLevel (один ценовой уровень)
   ┌────────────────────────────────────┐
   │ head, tail: Option<u32>             │   интрузивный двусвязный FIFO-список
   │ total_qty: Qty                      │   суммарный объём уровня
   └────────────────────────────────────┘

   Node (в слабе): { order: RestingOrder, prev, next: Option<u32> }
```

- `bids` и `asks` упорядочены по цене (`BTreeMap`): лучшая цена — на конце дерева.
- Внутри уровня заявки связаны интрузивным двусвязным списком (`head`/`tail` →
  слоты в слабе): порядок поступления — это и есть временной приоритет. Вставка
  в хвост, сведение с головы.
- Узлы заявок живут в общей арене (`slab`) со списком свободных слотов —
  аллокации переиспользуются, без выделения памяти на заявку в установившемся режиме.
- `index` сопоставляет `OrderId → (сторона, слот)`, поэтому отмена отцепляет узел
  из списка за `O(1)`, без обхода уровня.

### Сложность

| Операция | Сложность | Примечание |
| --- | --- | --- |
| Лучший bid/ask | `O(log L)` | `L` — число ценовых уровней |
| Вставка остатка | `O(log L)` | поиск/создание уровня |
| Шаг сведения | `O(log L)` на уровень + `O(1)` на заявку | FIFO с головы интрузивного списка |
| Отмена | `O(log L)` | поиск уровня в дереве + отцепление узла из списка за `O(1)` |

## Алгоритм матчинга

Price-time priority: первой исполняется самая агрессивная цена, при равной цене —
заявка, поступившая раньше. Ядро — `OrderBook::match_against`:

```
match_against(taker_side, limit_price, qty):
    opp = asks если Buy иначе bids
    while qty > 0:
        best = min(asks) если Buy иначе max(bids)      # лучшая встречная цена
        if best отсутствует: break                      # ликвидность кончилась
        if not crosses(limit_price, best): break        # цена больше не пересекается
        level = opp[best]
        while qty > 0 и level не пуст:
            head = slab[level.head]                     # самый ранний мейкер
            traded = min(qty, head.qty)
            head.qty -= traded;  qty -= traded
            emit Trade(maker=head.id, price=best, qty=traded)
            if head.qty == 0:                           # узел исчерпан:
                index.remove(head.id)                   #   снять из индекса,
                level.head = head.next; free(slot)      #   отцепить голову, вернуть слот
        if level пуст: удалить уровень best
    return qty                                          # неисполненный остаток
```

Условие пересечения `crosses`:

- market-заявка (`limit_price = None`) — пересекает всегда;
- `Buy` — `limit_price >= best_ask`;
- `Sell` — `limit_price <= best_bid`.

Тот же предикат вынесен в `OrderBook::would_cross` и используется post-only-гейтом в
движке: заявка-«только мейкер» отклоняется до приёма, если немедленно свелась бы.

Сделка исполняется по цене мейкера (`best`) — стоящего в книге, по правилу
price-time. Полностью исполненный мейкер тут же снимается из `index`, а его слот
возвращается в список свободных слотов слаба.

Инвариант: после обработки любой команды книга **не скрещена** — встречная заявка,
которая пересекла бы спред, обязательно свелась бы при поступлении (проверяется
тестом `book_is_never_crossed_after_matching`).

## Сквозной пример

Книга: ask `101 ×10`, ask `102 ×5`, bid `100 ×7`.
Приходит агрессивный `Buy` лимит `101 ×12` (`Gtc`):

1. Gateway: ок. Sequencer: `seq=4`, `order_id=4`. → `Accepted`.
2. Матчинг против asks: лучший ask `101` пересекается (`101 >= 101`) → сделка `101 ×10`.
   Следующий ask `102` уже не пересекается (`101 < 102`) → стоп. Остаток `2`.
3. `Limit` + `Gtc`, остаток `>0` → встаёт в книгу как bid `101 ×2`. → `Resting`.

Итог книги: bid `101 ×2`, bid `100 ×7`, ask `102 ×5`, спред `1`.
(Ровно этот сценарий печатает `examples/basic.rs`.)

## Где параллелизм

Внутри одной книги — никогда: это разрушило бы детерминизм. Масштабирование —
горизонтальное, шардированием по инструментам: на каждый инструмент свой
однопоточный `Clob`, а распределение и сетевой приём — слой выше (см. ROADMAP, v0.5).
