# Архитектура

## Обзор

`clob` — детерминированный движок центральной книги лимитных заявок, оформленный как
конвейер из четырёх стадий. Каждая команда проходит стадии по порядку и порождает
вектор событий.

```
                    ┌──────────┐   ┌────────────┐   ┌──────────────────┐   ┌──────────┐
   Command  ─────▶  │ Gateway  │─▶ │ Sequencer  │─▶ │ Matching Engine  │─▶ │  Output  │ ─────▶ Vec<Event>
(New/Cancel/Modify) └──────────┘   └────────────┘   └──────────────────┘   └──────────┘
                    валидация и     присвоение        ордербук +            события:
                    нормализация    seq и order_id    price-time матчинг    Trade / Resting / ...
```

Связывает стадии тип [`Clob`](../src/clob.rs). Публичный API минимален:

```rust
let mut clob = Clob::new();
let events: Vec<Event> = clob.submit(Command::New(NewOrder::limit(Side::Buy, 101, 5)));
```

## Принципы

1. **Детерминизм.** Один инструмент обрабатывается одним потоком в строгом порядке
   номеров последовательности. Одинаковый вход → одинаковый выход, всегда. Это даёт
   воспроизводимость, аудит, реплики и (в перспективе) восстановление по журналу.
2. **Целочисленная математика.** Цены — в тиках, количества — в лотах (`u64`).
   Никаких `f64`: денежные расчёты должны быть точными и повторяемыми.
3. **События на выходе, а не мутации на входе.** Движок не отдаёт наружу изменяемое
   состояние — он возвращает поток событий, естественный для клиринга, market data и журнала.
4. **Параллелизм — через шардирование по инструментам**, а не через потоки внутри одной книги.

## Стадии конвейера

### Gateway — [src/gateway.rs](../src/gateway.rs)

Первый барьер. Проверяет корректность команды до того, как она дойдёт до движка:

- `qty == 0` → `RejectReason::ZeroQuantity`;
- нулевая цена → `RejectReason::InvalidPrice`: лимитная заявка с `price == 0`, стоп с
  `trigger == 0`, стоп-лимит с `trigger == 0` или `price == 0`;
- `Modify` с `qty == 0` или `price == 0` отклоняется по тем же правилам;
- отмена проходит всегда (существование заявки проверяет движок).

Сюда же логично добавлять правила инструмента (размер тика/лота, ценовые коридоры,
pre-trade risk) — структура без полей оставлена расширяемой.

### Sequencer — [src/sequencer.rs](../src/sequencer.rs)

Присваивает каждому событию монотонный `seq`, а каждой новой заявке — уникальный
`order_id` (начиная с 1). Это сердце детерминизма: порядок фиксируется здесь и далее
не меняется. `seq` используется и как логическая метка времени.

### Matching Engine — [src/engine.rs](../src/engine.rs)

Применяет провалидированную и пронумерованную команду к ордербуку и порождает события.
Отвечает за семантику типов заявок и time-in-force:

- **FOK** — предпроверка `available_qty`; если полностью исполнить нельзя, заявка
  отклоняется (`InsufficientLiquidity`) и в книгу не попадает.
- **Post-only** — предпроверка `would_cross`; если лимит немедленно пересёк бы спред,
  заявка отклоняется (`WouldCross`) до `Accepted` и в книгу не попадает (`Market`
  считается пересечением всегда). Иначе ведёт себя как `Gtc` — встаёт в книгу.
- Иначе — `Accepted`, затем сведение со встречной стороной (события `Trade`).
- После сведения:
  - остаток `0` → `Filled`;
  - остаток `>0` и это `Limit` / `Iceberg` + (`Gtc` / `PostOnly`) → встаёт в книгу
    (`Resting`); для `Iceberg` в книге показывается только видимый peak, остальное —
    в скрытый резерв;
  - иначе (`Market`, `Ioc`, недопрошедший `Fok`) → остаток отменяется (`Canceled`).

Отмена: `execute_cancel` снимает заявку из книги (`Canceled`) либо отклоняет
несуществующую (`UnknownOrder`).

Изменение (amend): `execute_modify` находит стоящую заявку (иначе `UnknownOrder`) и
эмитит `Modified`. Уменьшение количества при той же цене — правка на месте за `O(1)`
с сохранением приоритета (далее `Resting` с новым объёмом). Смена цены или увеличение
количества — потеря приоритета: заявка снимается и с тем же `order_id` заново проходит
сведение (при пересечении спреда — `Trade`, затем `Filled` или `Resting`). Так книга
после amend остаётся нескрещённой.

Стоп-заявки (`Stop` / `StopLimit`) не попадают в основную книгу сразу: движок «паркует»
их в отдельной книге стопов ([src/stops.rs](../src/stops.rs)) и эмитит `Accepted`. Триггер
привязан к **цене последней сделки**: buy-stop активируется при `last >= trigger`, sell-stop —
при `last <= trigger`. После любой команды, породившей сделку (а также сразу после приёма
стопа), движок прогоняет сработавшие стопы: по каждому — `Triggered`, затем обычное сведение
(`Stop` — как рыночная, `StopLimit` — как лимит с тем же TIF) через тот же путь `settle`/`precheck`,
что и `New`. Сделки активированной заявки двигают цену последней сделки, поэтому активация
**каскадна**: один стоп может потянуть следующий. Каскад детерминирован (порядок активации —
по времени приёма) и конечен (множество спящих стопов строго убывает). События активации
тегируются `seq` текущей команды, заявка опознаётся по `order_id`. `Cancel` снимает спящий
стоп; `Modify` спящего стопа пока отклоняется (`UnknownOrder`).

Iceberg-заявки (`Iceberg { display }`) встают в книгу как обычный лимит, но показывают
только видимую часть (peak, `display`); остаток объёма лежит в скрытом резерве (сторонний
индекс в книге) и не виден в `depth()` / `len()` / `available_qty()`. Когда видимый peak
полностью сведён, из резерва доливается новый peak `min(display, hidden)` и ставится **в
хвост** своего ценового уровня — позади всех уже отображённых заявок, то есть с потерей
временного приоритета (стандартное правило айсберга). Достаточно крупный встречный приказ
проходит весь айсберг за один вызов `match_against`, послойно. Долив меняет состояние книги,
но событий не порождает. Как тейкер айсберг сводится на полный `qty` (как лимит); `Fok`
видит только отображённый объём (скрытый резерв в проверку ликвидности не входит). `Modify`
айсберга трактует `qty` как новый полный объём, сохраняет `display` и переставляет заявку
заново (теряя приоритет).

### Output — [src/output.rs](../src/output.rs)

Единый перечень событий `Event`:

| Событие | Когда |
| --- | --- |
| `Accepted` | заявка принята движком |
| `Trade` | состоялась сделка (тейкер ↔ мейкер, цена, объём) |
| `Resting` | остаток встал в книгу |
| `Filled` | заявка исполнена полностью |
| `Canceled` | заявка/остаток снят |
| `Modified` | заявка изменена (amend); далее идут события исхода |
| `Triggered` | стоп-заявка сработала; далее идут события исхода |
| `Rejected` | отказ (gateway, нехватка ликвидности для FOK или пересечение спреда для post-only) |

## Структура ордербука — [src/book.rs](../src/book.rs)

```
                 OrderBook
   ┌─────────────────────────────────────┐
   │ bids:  BTreeMap<Price, PriceLevel>   │   максимальная цена = лучший bid
   │ asks:  BTreeMap<Price, PriceLevel>   │   минимальная цена = лучший ask
   │ slab:  Vec<Node> + список свободных   │   арена узлов заявок
   │ index: HashMap<OrderId, {side, slot}> │   поиск узла для отмены за O(1)
   │ reserves: HashMap<OrderId,{disp,hid}> │   скрытые части iceberg-заявок
   └─────────────────────────────────────┘
                    │
                    ▼  PriceLevel (один ценовой уровень)
   ┌────────────────────────────────────┐
   │ head, tail: Option<u32>             │   интрузивный двусвязный FIFO-список
   │ total_qty: Qty                      │   суммарный объём уровня
   └────────────────────────────────────┘

   Node (в слабе): { order: RestingOrder, prev, next: Option<u32> }
```

- `bids` и `asks` упорядочены по цене (`BTreeMap`): лучшая цена — на конце дерева.
- Внутри уровня заявки связаны интрузивным двусвязным списком (`head`/`tail` →
  слоты в слабе): порядок поступления — это и есть временной приоритет. Вставка
  в хвост, сведение с головы.
- Узлы заявок живут в общей арене (`slab`) со списком свободных слотов —
  аллокации переиспользуются, без выделения памяти на заявку в установившемся режиме.
- `index` сопоставляет `OrderId → (сторона, слот)`, поэтому отмена отцепляет узел
  из списка за `O(1)`, без обхода уровня.
- `reserves` держит скрытые части iceberg-заявок (`OrderId → {display, hidden}`):
  видимый peak — обычный узел в слабе и в `total_qty` уровня, а резерв лежит отдельно
  и в глубину не входит. Запись появляется только у айсбергов с непустым резервом.

### Сложность

| Операция | Сложность | Примечание |
| --- | --- | --- |
| Лучший bid/ask | `O(log L)` | `L` — число ценовых уровней |
| Вставка остатка | `O(log L)` | поиск/создание уровня |
| Шаг сведения | `O(log L)` на уровень + `O(1)` на заявку | FIFO с головы интрузивного списка |
| Отмена | `O(log L)` | поиск уровня в дереве + отцепление узла из списка за `O(1)` |

## Алгоритм матчинга

Price-time priority: первой исполняется самая агрессивная цена, при равной цене —
заявка, поступившая раньше. Ядро — `OrderBook::match_against`:

```
match_against(taker_side, limit_price, qty):
    opp = asks если Buy иначе bids
    while qty > 0:
        best = min(asks) если Buy иначе max(bids)      # лучшая встречная цена
        if best отсутствует: break                      # ликвидность кончилась
        if not crosses(limit_price, best): break        # цена больше не пересекается
        level = opp[best]
        while qty > 0 и level не пуст:
            head = slab[level.head]                     # самый ранний мейкер
            traded = min(qty, head.qty)
            head.qty -= traded;  qty -= traded
            emit Trade(maker=head.id, price=best, qty=traded)
            if head.qty == 0:                           # узел исчерпан:
                index.remove(head.id)                   #   снять из индекса,
                level.head = head.next; free(slot)      #   отцепить голову, вернуть слот
        if level пуст: удалить уровень best
    return qty                                          # неисполненный остаток
```

Для iceberg-заявки шаг `if head.qty == 0` не удаляет узел, а доливает видимый peak из
скрытого резерва (`min(display, hidden)`) и переносит узел **в хвост** уровня: скрытая
часть встаёт в очередь заново, позади уже отображённых заявок. Узел удаляется лишь когда
резерв исчерпан. Резерв строго убывает, поэтому долив конечен.

Условие пересечения `crosses`:

- market-заявка (`limit_price = None`) — пересекает всегда;
- `Buy` — `limit_price >= best_ask`;
- `Sell` — `limit_price <= best_bid`.

Тот же предикат вынесен в `OrderBook::would_cross` и используется post-only-гейтом в
движке: заявка-«только мейкер» отклоняется до приёма, если немедленно свелась бы.

Сделка исполняется по цене мейкера (`best`) — стоящего в книге, по правилу
price-time. Полностью исполненный мейкер тут же снимается из `index`, а его слот
возвращается в список свободных слотов слаба.

Инвариант: после обработки любой команды книга **не скрещена** — встречная заявка,
которая пересекла бы спред, обязательно свелась бы при поступлении (проверяется
тестом `book_is_never_crossed_after_matching`).

## Сквозной пример

Книга: ask `101 ×10`, ask `102 ×5`, bid `100 ×7`.
Приходит агрессивный `Buy` лимит `101 ×12` (`Gtc`):

1. Gateway: ок. Sequencer: `seq=4`, `order_id=4`. → `Accepted`.
2. Матчинг против asks: лучший ask `101` пересекается (`101 >= 101`) → сделка `101 ×10`.
   Следующий ask `102` уже не пересекается (`101 < 102`) → стоп. Остаток `2`.
3. `Limit` + `Gtc`, остаток `>0` → встаёт в книгу как bid `101 ×2`. → `Resting`.

Итог книги: bid `101 ×2`, bid `100 ×7`, ask `102 ×5`, спред `1`.
(Ровно этот сценарий печатает `examples/basic.rs`.)

## Market data — снимки, инкрементальные обновления и лента сделок — [src/marketdata.rs](../src/marketdata.rs)

Market data — это **read-проекция** книги для внешних наблюдателей, отдельная от приватного
потока событий: движок книгу пишет, market data её только читает. Реализована как два метода
на `Clob` поверх публичных `book()` / `current_seq()`, без изменений детерминированного ядра:

- `l2_snapshot(depth)` — **market-by-price**: агрегированная глубина по ценовым уровням
  (`L2Snapshot` с `bids` / `asks` из `L2Level { price, qty }`), лучшая цена первой, не более
  `depth` уровней на сторону. Источник — `OrderBook::depth`.
- `l3_snapshot()` — **market-by-order**: книга по отдельным заявкам (`L3Snapshot` из
  `L3Order { id, side, price, qty }`), best-first по цене и FIFO внутри уровня — то есть видна
  позиция в очереди. Источник — `OrderBook::resting_orders` (стабильная сортировка по цене
  сохраняет порядок очереди внутри уровня).

Оба снимка тегируются текущим `seq`, чтобы потребитель мог упорядочить их относительно будущих
инкрементальных обновлений (следующий шаг v0.4). Проекция **публичная и обезличенная**: для
iceberg-заявок отдаётся только видимый peak — скрытый резерв в L2/L3 не попадает (приватность
определяется тем, что участник *выставил* в книгу, а не гранулярностью фида). L2 — это агрегация
L3 по цене: `sum(L3 qty по уровню) == L2 qty` (инвариант проверяется тестом
`l2_equals_l3_aggregated`).

### Инкрементальные L2-обновления — `L2Update` / `L2Feed`

Снимок — это вся книга; чтобы не пересылать её при каждом изменении, market data умеет отдавать
**инкрементальные L2-дельты**. `L2Feed` — stateful read-проекция: `apply(&events, book)` превращает
`Vec<Event>` одной команды в `L2Update { seq, bids, asks }` — список **только изменённых** ценовых
уровней (уровень с `qty == 0` означает удаление; цены — best-first на каждой стороне). Кадр несёт
`seq` команды, общий якорь со снимком: потребитель берёт `l2_snapshot` на `seq = N` (или сеет фид
тем же состоянием через `L2Feed::from_book`) и применяет последующие дельты, держа локальную книгу
в синхроне без повторной пересылки всей глубины.

Какие уровни затронуты, фид выводит **из событий**, не сканируя книгу: у `Trade` — цена на стороне
мейкера (`taker_side.opposite()`); у `Resting` — сторона и цена вставшего остатка; у `Canceled` /
`Filled` / `Modified` — прежняя позиция заявки из внутреннего зеркала `order_id → (side, price)`
(эти события несут только `order_id`). Новый агрегат каждого затронутого уровня **читается из книги**
(`OrderBook::level_qty`), а не накапливается из событий, поэтому дельта точна и в двух случаях,
невидимых по потоку событий: **айсберг-долив** (события нет, но долив всегда происходит на трейд-цене,
а та уже в множестве затронутых уровней) и **modify-репрайс** (старый уровень добавляется по `Modified`
прежде, чем последующий `Resting` обновит зеркало на новую цену). Проекция остаётся обезличенной —
скрытого резерва айсберга в книге нет, и в дельты он не попадает. Детерминизм сохранён: множество
затронутых уровней — `BTreeSet`, выход явно отсортирован, итерация `HashMap` на вывод не влияет.

Фид со-локален с движком (читает книгу).

### Лента сделок (trade tape) — `TradeTape` / `TapeTrade` — [src/tape.rs](../src/tape.rs)

Снимки и L2-дельты описывают **состояние книги**; лента сделок — это отдельный канал **потока
исполнений**. `TradeTape::apply(&events)` извлекает из событий одной команды по одному обезличенному
принту `TapeTrade { seq, price, qty, taker_side }` на каждый `Event::Trade` (в порядке исполнения —
при свипе нескольких уровней best price first), возвращает принты команды и удерживает их в
ограниченной кольцевой истории (`new()` — без предела, `bounded(cap)` — последние `cap`; чтение —
`recent()` от старых к новым, `last()`, `len()`). Каждый принт несёт `seq` команды — тот же якорь, что
у снимков и `L2Update`, так что каналы упорядочиваются между собой по `seq`.

В отличие от L2/L3-проекций лента **book-free**: `apply` берёт только `&[Event]` и книгу не читает —
ленту может вести потребитель, у которого есть лишь поток событий (то, чего со-локальный L2-фид пока
не умеет). Обезличенность здесь — о владельце и идентификаторах: id заявок в принт не попадают. Но
исполненный объём — публичный факт и печатается **полностью**: проход по айсбергу даёт принт на каждый
сведённый слой, включая объём из скрытого резерва. Это сознательная асимметрия с книжными проекциями —
книга прячет *стоящий* резерв (что участник выставил), а лента печатает *исполненное* (что произошло на
рынке). Лента не входит в снимки состояния (сделки — это поток, не состояние): при реплее журнала
команды переисполняются и `Trade`-события возникают заново, поэтому потребитель восстанавливает ту же
ленту из переигранного потока. Детерминизм сохранён — лента лишь проецирует уже детерминированный поток
событий.

Инкремент market-by-order (L3) с позицией в очереди и сквозная нумерация между data-каналами —
следующие шаги v0.4.

## Где параллелизм

Внутри одной книги — никогда: это разрушило бы детерминизм. Масштабирование —
горизонтальное, шардированием по инструментам: на каждый инструмент свой
однопоточный `Clob`, а распределение и сетевой приём — слой выше (см. ROADMAP, v0.5).

## Персистентность, снимки и реплей — [src/persist.rs](../src/persist.rs)

Надстройка над детерминированным ядром (v0.3). `PersistentClob` оборачивает `Clob`
и ведёт **write-ahead журнал** входных команд: команда сериализуется и сбрасывается на диск
(`fsync`) **до** того, как события вернутся вызывающему, — подтверждённая заявка переживает
падение процесса. При открытии состояние восстанавливается **реплеем**: записанный поток
команд переподаётся в свежий `Clob`. Поскольку движок детерминирован, книга, `order_id` и
`seq` воспроизводятся точно (отклонённые gateway команды тоже журналируются — они расходуют
`seq`, иначе нумерация при реплее разъехалась бы).

Формат журнала — собственный бинарный, `std`-only (без serde и внешних крейтов):

```
сегмент = [ magic "CLBW" (4) | версия u16 | base_seq u64 ]   заголовок один раз
          затем блоки:
          [ block_len u32 | rec_count varint | записи… | crc32 u32 ]   один блок = один fsync
запись  = [ tag u8 | (для New) флаги side|type|tif | поля varint по типу ]
```

Числовые поля — LEB128-varint ([src/codec.rs](../src/codec.rs)); тот же кодек переиспользуется
снимками. Кодирование/декодирование `Command` и заголовок — в
[src/journal.rs](../src/journal.rs); запись с групповым коммитом (`Journal`) и чтение
(`read_commands` / `read_segment`) — в [src/wal.rs](../src/wal.rs). При восстановлении читатель
проверяет `magic`/версию и CRC каждого блока; прерванная на полузаписи последняя запись (CRC не
сходится или блок неполон) отсекается — журнал восстанавливается до последней целой записи.

### Снимки (checkpoint) — [src/snapshot.rs](../src/snapshot.rs)

Чтобы восстановление не переигрывало весь журнал с нуля, `checkpoint()` сохраняет **снимок**
полного детерминированного состояния и затем **ротирует** журнал, оставляя только хвост:

1. `journal.commit()` — досбросить накопленный блок.
2. Записать снимок атомарно: во временный файл `<journal>.snap.tmp` → `fsync` → `rename` в
   `<journal>.snap`. Это точка фиксации чекпойнта.
3. `journal.rotate(N)` — заменить журнал свежим сегментом с `base_seq = N` (`N` — текущий `seq`),
   тоже через временный файл + `rename`. Старые команды (`seq ≤ N`) теперь только в снимке.

Снимок сериализует всё, что влияет на дальнейшую обработку: счётчики секвенсора `seq` и
`next_order_id` (последний не выводится из `seq` — `Cancel`/`Modify` тратят `seq`, но не
`order_id`), цену последней сделки (нужна для триггеров стопов), все стоящие заявки в порядке
приоритета вместе со скрытыми резервами айсбергов и спящие стопы. Формат — `magic "CLBS"` +
версия, varint-поля, единый кадр с CRC32 в конце.

Восстановление со снимком (`PersistentClob::open`):

```
open(journal, snapshot):
    (clob, applied) = снимок есть ? (restore(снимок), снимок.seq) : (Clob::new(), 0)
    (base_seq, commands) = read_segment(journal)
    для i-й команды:  seq = base_seq + i + 1
        if seq > applied:  clob.submit_into(команда)   # переигрываем только хвост
    journal = Journal::open_base(journal, applied)      # пустой/новый сегмент получит base = applied
```

**Согласование идемпотентно по `seq`** — это и есть крэш-безопасность чекпойнта. Применяются
только команды с `seq` больше покрытого снимком, поэтому неважно, успел ли `rotate` отработать:
если чекпойнт прервался после записи снимка, но до ротации, журнал всё ещё содержит команды
`seq ≤ N` — они просто пропускаются (а не применяются повторно). Команды `seq > N` всегда лежат
в журнале и переигрываются. Битый снимок (CRC не сходится) отклоняется как `CorruptSnapshot`:
тогда журнал — единственный источник истины, и молчаливо подменять состояние нельзя.

Инвариант детерминизма не нарушен: слой персистентности делает ввод-вывод, но не вводит в ядро
ни часов, ни потоков, ни зависящей от `HashMap` итерации (снимок обходит заявки по ценовым
уровням и FIFO внутри уровня — детерминированный порядок); кадрирование, коммит и чекпойнт
управляются счётчиком записей и явным вызовом приложения, а не стенными часами.
