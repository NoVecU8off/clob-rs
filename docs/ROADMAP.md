# Что предстоит сделать

Этапы ориентировочные, порядок может меняться. Отметки: `[ ]` — не начато,
`[~]` — в работе, `[x]` — готово. Текущее состояние — в [STATUS.md](STATUS.md).

## Область крейта

`clob` — чистый встраиваемый матчинг-движок: только `std`, детерминированное
однопоточное ядро, события на выходе. Ядро уже представляет собой **законченный
протестированный блок** (этапы v0.2–v0.4 закрыты). Граница крейта проста: всё, что
тянет внешнюю зависимость или меняет модель исполнения (async-рантайм, потоки, сеть),
живёт **вне ядра** — отдельным крейтом этажом выше (см. раздел «Вне ядра — отдельный
крейт» ниже и принцип «слой выше» в [ARCHITECTURE.md](ARCHITECTURE.md)). Дальнейшая
работа в самом крейте — только доменная полнота на `std`.

## v0.2 — Производительность и типы заявок

- [x] **Интрузивный список на ценовом уровне** → отмена внутри уровня за `O(1)`
      (узлы в слабе-арене со списком свободных слотов; снят прежний `O(n)` скан).
- [x] **Команда `Modify` / amend** — изменение цены/количества; смена цены или
      увеличение объёма теряет временной приоритет, уменьшение — сохраняет.
- [x] **Post-only** — отклонять заявку, если она немедленно пересекла бы спред (maker-only).
- [x] **Stop / stop-limit** — отложенные заявки, активируемые по триггерной цене
      (по цене последней сделки; срабатывание каскадное, событие `Triggered`).
- [x] **Iceberg** — видимая (peak) и скрытая (reserve) части объёма; при исчерпании
      видимой части peak доливается из резерва в хвост уровня (теряя приоритет).
- [x] Пул переиспользуемых аллокаций в матчинге (слаб со списком свободных слотов;
      убран `Vec` под исполненные id).

## v0.3 — Надёжность и реплей

- [x] **Журнал событий (event sourcing)** — запись входного потока команд в append-only
      WAL (`Journal`): собственный бинарный формат с varint, покадровый CRC32, групповой
      коммит с `fsync`. Обёртка `PersistentClob` журналирует команду write-ahead — durable
      до возврата событий.
- [x] **Реплей** — восстановление состояния переподачей журнала в свежий `Clob`
      (`PersistentClob::open`); за счёт детерминизма книга, `order_id` и `seq` воспроизводятся
      точно. Битый хвост от прерванной записи отсекается по CRC. Горячий резерв (реплика) —
      тем же механизмом чтения потока команд.
- [x] **Снимки (snapshots)** состояния книги для ускорения восстановления (`checkpoint()`
      пишет снимок полного состояния и ротирует журнал; `open` грузит снимок и переигрывает
      только хвост журнала; согласование идемпотентно по `seq`, чекпойнт крэш-безопасен). *(фаза 2 v0.3)*
- [x] Версионирование формата: журнал — `magic "CLBW"` + версия в заголовке сегмента;
      снимки — `magic "CLBS"` + версия, общий кадр с CRC32.

## v0.4 — Market data

- [x] **L2-снимок** (агрегированная глубина по уровням) и **L3** (по заявкам) —
      `Clob::l2_snapshot` / `Clob::l3_snapshot`, оба тегированы `seq`; read-проекция в
      `src/marketdata.rs`, скрытый резерв айсбергов в снимки не попадает.
- [x] **Инкрементальные L2-обновления** (market-by-price): дельты только изменённых
      уровней (`L2Update` / `L2Feed`) поверх снимка с общим `seq`; ядро не затронуто.
- [x] **Инкрементальные L3-обновления** (market-by-order, с позицией в очереди): пер-заявочные
      дельты `L3Delta` (`Added` / `Reduced` / `Removed`) в `L3Update` через `L3Feed`
      (`src/l3feed.rs`). Затронутые уровни выводятся из событий (как у L2), а порядок очереди
      внутри уровня сверяется с книгой (`OrderBook::level_orders`); долив айсберга и потеря
      приоритета при amend выражаются как remove-then-add (перестановка в хвост уровня).
- [x] **Поток сделок (trade tape)** как отдельный канал — `TradeTape` извлекает из потока событий
      публичные обезличенные принты (`TapeTrade { seq, price, qty, taker_side }`, по одному на
      `Trade`-эвент) и ведёт ограниченную кольцевую историю. Канал **book-free**: `apply` берёт только
      события, без доступа к книге. Принт несёт `seq` команды — общий якорь с книжным каналом.
- [x] **Консистентность номеров последовательности между data-каналами** — все каналы (снимки
      L2/L3, инкременты `L2Update` / `L3Update`, принты `TapeTrade`) якорятся на `seq` команды
      через единый `command_seq`: для одной команды все каналы несут один `seq`, равный
      `Clob::current_seq()` после неё. Потребитель применяет инкременты с `seq` больше, чем у
      снимка, и сводит каналы между собой по общему `seq`.

## v0.5 — Доменная полнота движка (`std`-only)

Доменная логика самого движка — без внешних зависимостей, ядро остаётся чистым и
детерминированным.

- [x] **Счёт/владелец заявки** и **self-trade prevention** (запрет самосведения):
      `owner: AccountId` + `stp: StpMode` в модели заявки; STP срабатывает при сведении по политике
      **агрессора** (cancel-taker / cancel-maker / cancel-both), по каждому встречному мейкеру.
      `owner` переживает снимок/реплей и не утекает в market data. Политика `decrement` (срез обоих
      на overlap) и STP на `Modify` — отложены.
- [ ] **Pre-trade risk** в Gateway: размер тика/лота, ценовые коридоры, лимиты позиции.
- [ ] **Комиссии** maker/taker и их расчёт в событиях сделок.

## Качество и инструментарий

Эти пункты тянут внешние крейты, поэтому в зависимости ядра **не входят** — живут как
`std`-only примеры или отдельный dev-харнесс (правило zero-dependency в `CLAUDE.md`).

- [ ] Бенчмарки латентности (p50/p99/p99.9) — как `examples/` на `std::time`
      (criterion как зависимость не добавляем).
- [ ] **Property-based тесты** и **фаззинг** конвейера команд — отдельным dev-харнессом
      вне крейта (proptest / fuzz тянут зависимости).

## Вне ядра — отдельный крейт (`clob-server`)

Сетевой и масштабный слой **не входит** в крейт `clob`: он потянул бы tokio и
async-рантайм, нарушив и zero-dependency, и однопоточный детерминизм ядра. Когда
понадобится — отдельный крейт в воркспейсе, зависящий от чистого `clob` (ядро при этом
tokio не берёт никогда):

- [ ] **Асинхронный шлюз** (tokio): приём команд по TCP/WebSocket, рассылка событий.
- [ ] **Шардирование по инструментам** — один однопоточный `clob` на инструмент;
      распределение и приём — слоем выше.
- [ ] Бинарный протокол кодирования команд/событий «на провод».
- [ ] Backpressure и ограничение скорости на шлюзе.

## Осознанно вне области (пока)

- Клиринг и расчёты (settlement) — отдельная подсистема ниже по потоку.
- Кросс-инструментные стратегии матчинга (спреды, мультилег).
- Pro-rata и иные алгоритмы распределения (сейчас только price-time); закладывается
  через абстракцию политики уровня, когда понадобится.
